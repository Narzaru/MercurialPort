# CLAUDE.md

Плагин **Mercurial Port** (репозиторий `Narzaru/MercurialPort`, артефакт `mercurial-port`;
прежнее имя `hgrider` пришлось сменить — имя плагина не должно содержать названий продуктов
JetBrains, а `hgrider` содержит `rider`) — инструменты Mercurial
для JetBrains IDE (используется в Rider). Порт расширения
HgVs для Visual Studio. Практическая цель — «Upsource внутри IDE»: ревью собственной ветки по файлам
с отметками «просмотрено».

## Сборка и проверка

```bash
./gradlew compileKotlin     # быстрая проверка компиляции
./gradlew test              # юнит-тесты (нужна сеть: junit и test-framework не в репозитории)
./gradlew buildPlugin       # артефакт build/distributions/mercurial-port-<version>.zip
./gradlew runIde            # запуск IDE с плагином
```

Версия задаётся в `gradle.properties`, целевая платформа — `intellijIdea("2025.2.6.2")` в
`build.gradle.kts`, версия Gradle-плагина платформы — в `settings.gradle.kts`.

Установка для проверки: `Settings → Plugins → ⚙ → Install Plugin from Disk…` → zip из
`build/distributions`, затем перезапуск IDE.

Сборка для установки — **всегда** через скрипт, он сам поднимает версию:

```powershell
.\build-plugin.ps1                 # patch +1 и buildPlugin
.\build-plugin.ps1 -Version 0.1.0  # версия явно
.\build-plugin.ps1 -SkipBump       # пересобрать текущую
```

При неизменной версии zip называется так же, в списке плагинов ничего не меняется, и старая
установка неотличима от новой — так уже вышло, что несколько итераций правок проверялись на
сборке двухчасовой давности. И `compileKotlin` артефакт **не** обновляет: если правки проверяются
в установленном плагине, нужен `buildPlugin`. Убедиться, что установлено именно новое, можно так:

```bash
unzip -p "$APPDATA/JetBrains/Rider<версия>/plugins/mercurial-port/lib/mercurial-port-<version>.jar" \
  com/narzaru/mercurial/history/HgFileHistoryPanel.class | grep -c "<новая строка из правки>"
```

Ошибки времени выполнения ищутся в `%LOCALAPPDATA%\JetBrains\Rider<версия>\log\idea.log` —
падение в конструкторе панели проявляется как пустое тул-окно с «Nothing to show», а не как диалог.

## Структура

Корень пакетов — `com.narzaru.mercurial`.

| Пакет | Содержимое |
|---|---|
| `hg` | Запуск `hg`, разбор и декодирование вывода, пути, настройки плагина |
| `changes` | Тул-окно **Hg Changes** — дерево изменений, ревью-отметки, TODO-режим |
| `history` | Тул-окно **Hg File History** — `hg log -f` по файлу |
| `export` | Действия «Hg Export» в меню Tools |
| `model` | Модели данных (`HgFileItem`, `HgDiffStat`, режимы) |

Регистрация тул-окон, страницы настроек и действий — `src/main/resources/META-INF/plugin.xml`.

Панели (`HgChangesPanel`, `HgFileHistoryPanel`) отвечают только за UI и оркестровку. Всё, что можно
проверить без запущенной IDE, вынесено отдельно и покрыто тестами в `src/test/kotlin`:

- разбор вывода `hg` — `HgStatusParser`, `HgDiffStatParser`, `HgLogParser`, `HgOutputDecoder`;
- пути — `HgPaths` (`hg` отдаёт `/`, платформа на Windows `\`, регистр может отличаться);
- состояние окна изменений — `ReviewState` (за интерфейсом `ReviewedPathsStore`), `PathFilter`,
  `ChangesSettings`, `StatusTextFormatter`;
- дерево и отрисовка — `ChangesTreeBuilder`, `ChangesTreeRenderers`, `TextFitter`.

Новую логику имеет смысл добавлять туда же, а не в панель: внутри Swing-компонента её не вызвать
из теста.

## Ключевые решения

### Кодировки

`HgOutputDecoder` декодирует вывод **построчно**: сначала строгий UTF-8, при ошибке — кодировка из
`HgSettings.fallbackEncoding`. По умолчанию это ANSI-кодировка ОС (`sun.jnu.encoding`, на русской
Windows — cp1251), а **не** `Charset.defaultCharset()`: в JDK 18+ последняя равна UTF-8, из-за чего
сообщения коммитов в cp1251 превращались в «вопросики». Настраивается в
`Settings → Tools → Mercurial Port`.

Декодер также срезает UTF-8 BOM в начале вывода: `hg cat` отдаёт файл как есть, а платформа в
редакторе BOM снимает — иначе первая строка диффа всегда «отличалась» на невидимый U+FEFF.

### Дифф

Вкладками владеет **`diff/HgDiffTabManager`** — один на проект, для обоих окон. Раньше каждая панель
вела свою «переиспользуемую вкладку», и на экране оказывалось два диффа сразу. Менеджер держит слот
(общий или по окну — переключается настройкой, по умолчанию общий), активирует вкладку при совпадении
ключа содержимого и закрывает предыдущую: платформа вкладки сама не переиспользует.

Используется `DiffEditorTabFilesManager.showDiffFile(file, focusEditor = false)`, чтобы фокус оставался
в списке файлов. **Но при пустом редакторе этот вызов не показывает ничего** — области редактора ещё
не существует; поэтому результат проверяется через `isFileOpen`, и вкладка открывается обычным
`openFile`. Заголовок вкладки — только имя файла.

Новые (`A`) и неотслеживаемые (`?`) файлы сравниваются с `DiffContentFactory.createEmpty()`, а не
считаются ошибкой; симметрично для удалённых локально.

### Стоимость запуска hg

`hg version` на этой машине — ~265 мс: это старт интерпретатора, до всякой полезной работы.
Столько же стоит любой `hg cat`, а само чтение файла на этом фоне бесплатно. Поэтому дифф
ускоряется не оптимизацией команды, а тем, что её не запускают:

- содержимое базовой ревизии кэшируется (`HgContentCache`, LRU) — оно неизменно; кэшируется и
  отрицательный ответ «файла в ревизии не было», он стоит того же запуска;
- соседние строки списка дочитываются заранее (`prefetchAround`), поэтому при ходьбе стрелками
  следующий дифф к моменту нажатия уже готов;
- кэш сбрасывается на каждый `refresh()` **безусловно**: базовая ревизия записывается символически
  (`.`), и после коммита то же выражение указывает на другое содержимое — по ключу устаревшую
  запись не отличить.

### Что считать «изменениями ветки»

Upsource для ревью «первая ревизия ветки … текущая» показывает дифф **от точки ответвления**
(`p1(first(branch(.)))`), но только по файлам, которых касались **собственные ревизии ветки**
(`only(., max(ancestors(.) and branch(p1(first(branch(.))))))`). Одной базы мало: после слияния
родительской ветки в свою всё, что родитель успел наменять до слияния, тоже отличается от точки
ответвления — на реальной ветке это 889 файлов и `+20585 −8168` вместо 89 и `+6816 −144`. Одного
merge base тоже мало: он даёт правильный список, но не те числа, что в Upsource.

У ревизии слияния `{files}` содержит только то, что правилось при слиянии, поэтому разрешение
конфликтов в списке остаётся, а просто влитые файлы — нет. Этим множеством ограничены оба режима
ветки; сравнение без ограничения осталось в режиме `vs <branch>`.

`hg status --rev` считает изменённым файл, у которого после слияния новая ревизия filelog при
прежнем содержимом: дифф по нему пуст, такие строки гасятся штатной пометкой `♦`.

### Производительность Hg Changes

- `hg diff --git` по целой ветке — это мегабайты. Разбор идёт **по байтам** в
  `collectDiffStats`; декодирование всего вывода в строку со `split` подвешивало IDE.
- Статистика `+N −M` считается **после** показа дерева (`loadDiffStats`), список не ждёт диффа.
  Устаревшие результаты отсекаются счётчиком поколений (`statsRequestId`).
- Рендереры колонок переиспользуют один компонент — создание Swing-компонента на каждую ячейку
  заметно тормозит дерево в тысячи строк.

### Swing-ловушки, на которые уже наступали

- **Из рендерера нельзя звать `tree.getRowBounds()`** — `TreeUI` для вычисления границ строки снова
  вызывает рендерер, получается бесконечная рекурсия и `StackOverflowError` в EDT (внешне — артефакты
  отрисовки по всему окну IDE). Отступ уровня считается через `node.level`.
- **Свойства, используемые из `init`, должны быть объявлены выше него.** `by lazy` не спасает:
  делегат — тоже поле и инициализируется по порядку объявления. Так падали рендереры колонок.
- **`tree.tableHeader = null` ломает `TreeTable`** при перестройке колонок. Заголовок снимается через
  `scrollPane.setColumnHeaderView(null)`.
- **`TreeTable` отдаёт события колонки дерева самому дереву**, и двойной клик по каталогу оно
  раскрывает без нашего участия. Свой `toggleExpand` на той же колонке сворачивал узел и тут же
  разворачивал обратно; в прочих колонках событие до дерева не доходит — там он нужен.
- **`TreeTable` не спрашивает рендерер у `ColumnInfo.getRenderer()`** — его надо задавать на
  `TableColumn.cellRenderer`.
- **`JBLabel` с `<html>` не переносит строки сам** — без заданной ширины предпочтительный размер
  считается по одной строке, и текст уезжает за границу окна. Страница настроек поэтому собрана на
  UI DSL (`panel { row { text(...) } }`), где перенос по словам штатный, а длинные пояснения живут
  в `comment` под полем.
- **`FlowLayout` внутри `BoxLayout` не переносит строки**, а обрезает их: предпочтительный размер
  считается одной строкой. Для этого написан `WrapLayout`.
- При скрытии колонки индексы на экране и в модели расходятся — сравнивать через
  `convertColumnIndexToModel`.

## Поведение UI (договорённости)

**Hg Changes**
- Дерево в стиле Upsource: группировка по каталогам, цепочки с одним потомком схлопываются
  (`Cad.Toolware.Tests/RayTracing`), у файлов `+N −M`, у каталогов — агрегаты и `просмотрено/всего`.
- Непросмотренные файлы жирные, просмотренные — серые и обычным начертанием (как и файлы без
  реальных изменений: и то, и другое — строки, до которых больше нет дела).
- **Одинарный клик — дифф, двойной — открыть файл.** Без задержек и без учёта модификаторов.
- **Выбор строки и есть просмотр**: одинарный клик и переход стрелками показывают дифф и ставят
  отметку. Клик обрабатывается сразу, переход стрелками — с паузой `SELECTION_DEBOUNCE_MS`, иначе
  зажатая стрелка пометит всю ветку и запустит по `hg cat` на строку. Отключается пунктом
  `Mark Reviewed on Open` в меню ⋮.
- Двойной клик **отменяет** дифф, заказанный первым из двух щелчков (`diffRequestId`), — иначе тот
  приходит из фонового потока следом и перебивает только что открытый файл. Полностью избежать
  диффа при двойном клике нельзя: он содержит одинарный, а задержек на клик здесь нет.
- Панель **не следит** за активным редактором — это пробовали и убрали. Закрытие файла и его диффа
  переключает редактор на соседнюю вкладку, панель считала это открытием и снова показывала дифф,
  то есть заново открывала только что закрытое.
- Клик по колонке-глазу переключает отметку; у каталога — сразу для всех файлов внутри. `Space`
  делает то же для выделения. Отметки хранятся в `PropertiesComponent` проекта и переживают refresh.
  Обычную активацию строки клик по глазу не запускает — иначе отметка ставилась бы и тут же снималась.
- Выделение переживает перестройку дерева (`renderFiltered` восстанавливает его по путям): отметка
  просмотра перерисовывает дерево целиком, и без этого место в списке терялось бы на каждом шаге.
- Длинный текст обрезается справа с многоточием, полный — в тултипе. Тултип считается **вне
  рендерера**, в `getToolTipText(MouseEvent)` самого `TreeTable` (плюс регистрация в `ToolTipManager`):
  рендереры переиспользуют один компонент, и выставленный в них `toolTipText` отдаётся от чужой строки.
- Файлы без реальных изменений скрыты, пока не включён `Show Unchanged`; неотслеживаемые — `Show Untracked`.
- Настройки редкого пользования — в меню ⋮ тул-окна (`ToolWindowEx.setAdditionalGearActions`).

**Hg File History**
- Панель следует за файлом в активном редакторе и за выбором в Hg Changes (общий вход
  `HgFileHistoryPanel.syncTo`, доступный через `HgFileHistoryService`). Контекстного меню у неё нет —
  оно было убрано намеренно, как и `Pin` с режимами `Diff Mode`: окно отвечает за полную историю
  файла, сравнения — задача Hg Changes.
- Шапка — как в Hg Changes: icon-тулбар (Refresh / Show Diff / Open) и мелкая строка
  `History: <файл>` + статус, без жирного заголовка.
- **Клик по строке — дифф.** Выделены две ревизии — сравниваются между собой. Двойной клик не
  задействован: открытие самой ревизии файла интереса не представляет (действие осталось только
  в тулбаре).
- Дифф ревизии показывает изменения самой ревизии: левая сторона — файл у первого
  родителя (`{p1rev}`), а не у следующей строки лога (при слияниях это разные ревизии). Путь у
  родителя берётся до переименования — `hg log -f` следует за rename, и `hg cat` со старым именем
  иначе падает. Добавление/удаление файла — пустая сторона диффа, а не ошибка.
- Пустая сторона здесь — **пустой документ того же типа**, а не `DiffContentFactory.createEmpty()`:
  с `EmptyContent` вкладка для init-коммита (у ревизии нет родителя, слева пусто) не открывалась.
- Панель следует **только за файлами на диске** (`isInLocalFileSystem`) и игнорирует смену вкладок,
  вызванную ею самой (`withoutFollow`). Иначе открытие своего же диффа (или закрытие предыдущего)
  переключало историю на другой файл: список моргал и пустел, выделение ревизии терялось, и
  `Open Diff` дальше молча ничего не делал. Hg Changes гасит слежение вокруг своих дифф-вкладок
  через `HgFileHistoryService.suppressFollow` — при закрытии диффа редактор выбирает соседний файл.
- Список при перезагрузке **не очищается**: старые строки держатся до прихода новых, устаревшие
  ответы `hg log` отсекаются счётчиком поколений.
- Пока тул-окно скрыто, `hg` не запускается.

## Стиль

- Комментарии и сообщения пользователю — по-русски, идентификаторы и CHANGELOG — по-английски.
- Комментарий объясняет **почему**, а не что делает строка; особенно для обходов платформенных
  ловушек из списка выше.
- CHANGELOG ведётся в разделе `[Unreleased]` (`Added` / `Changed`).
